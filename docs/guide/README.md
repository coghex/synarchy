# Synarchy guide scope

Owner instruction, 2026-09-29: accept the past as the baseline, assess the
present project against its vision, then evaluate ongoing work. This supplements
the installed guide workflow for this repository.

## Start from the cursor

Read [CURSOR.md](CURSOR.md), [the published vision](../vision.md), and the
repository instructions. Reports and their coverage are the durable record;
the cursor is their resumable summary. The initial manual registration accepts
history through its exact pin without claiming a fresh historical audit.

## First substantive assessment

Take a fresh pin with `guide.py start`. Establish the current project's position
against every vision principle using current code, its owners and consumers,
implemented contracts, and effective issue specifications. Assess the whole
experience and architecture across subsystem boundaries, including gameplay,
expeditions, information and UI, assets, continuity and performance evidence.
Use representative paths and focused checks; state limits explicitly rather
than claiming exhaustive correctness.

Review all open issues with their bodies and every comment, prioritizing work
about to be built. Open PRs supply prospective context and interactions. They
are not merged work or canonical PR approvals. Accepting history does not accept
an open specification or waive an existing qualification gate.

## Subsequent assessments

Review code merges and changed issue specifications since the cursor using the
installed bookkeeping. Also synthesize what those changes mean for the current
project as a whole: progress, cumulative drift, integration gaps and the next
unmet accepted goal. Carry readings forward only where their evidence remains
applicable; identify untouched areas and unfinished coverage.

Historical work need not be re-reviewed item by item. Current code remains
reviewable when it provides evidence of a present defect, cumulative problem,
or contradiction in a proposed issue. Keep missing future design and expected
unfinished delivery separate from defects.

## Vision and authority

Synarchy's published vision currently records explicit owner decisions but
still marks the full document incomplete and unapproved. Use those decisions
as directional context and expose unresolved choices. Do not silently promote
proposals or change implemented contracts. Note unpublished vision edits; the
published version remains the review reference until the owner changes it.

Standalone drafts and documentation landings are context, not review targets.
Guide remains advisory. Canonical issue/PR review gates own approval; tracker
writes and follow-up dispositions need the owner's authorization. Guide reports
and the cursor use `docs-wip`, and publication follows the repository's docs lane.
