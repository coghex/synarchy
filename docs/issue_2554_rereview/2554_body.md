## Background

FTS-6D of #2496, Phase 9, `critical path`, depends on #2551 (FTS-6C),
which must merge first. Its prerequisite chain supplies persisted faction
profiles, membership provenance, the relation authority, and owner-scoped
Lua operations. This issue adds profile requests at spawn ingress, the
local controller's roster team tag, and per-location occupant group tags.
Deliver the implementation, required documentation, and validation evidence
together in one PR.

Verified against `master` `293df10fb6e6` on 2026-09-10:

- `unit.spawn` accepts a legacy faction string in argument 4 or 5, with
  page and binding generation fixed at arguments 6 and 7
  (`src/Engine/Scripting/Lua/API/Units/Spawn.hs`). Portal spawns use
  `"player"`; the debug overlay uses `"debug"`.
- Both `spawnUnitContent` and `spawnEncounterUnitContent` in
  `scripts/locations.lua` independently default to `"hostile"`.
  `ruin_small` uses `count_range`, so its nomads take the dedicated
  encounter path. That path persists every successful roster prefix and
  retries only missing slots.
- Location instance integers start at 1 independently on each page.
  Durable location identity is `(WorldPageId, instance_id)`
  (`src/Location/Instance.hs`), not the integer alone.
- `Unit.Faction.Profile.relationFromTo` resolves live directed causes,
  then a shared non-null controller, then any shared tag, then base
  relations, then neutral. Tags have no separate culture/team precedence.
- Load reconciliation can legitimately change non-wire code in
  `World.Save.Types.fromUnitSnapshot` and `World.Load.Stage`.
  An empty diff under `src/World/Save` does not prove persistence safety.

Owner decisions:

- Only the engine's local controller may be requested in this slice,
  under one documented identity. Other controller requests fall back
  inertly as specified below.
- Nomads in different locations remain allied through their shared
  `nomad` tag. Applicable live relations retain their existing precedence;
  a hostile base-table entry alone does not override shared-tag alliance.
- Explicit location `player` and `debug` overrides retain their legacy
  control/capability behavior, with the location group tag added afterward
  and participating normally in relations.

## Requirements

1. **Profile ingress and compatibility.** `unit.spawn` accepts a profile
   request in either supported faction argument position, naming an
   optional local controller and optional extra tags with ownership.
   Start from the definition's FTS-3 default profile and add the requested
   controller/memberships. Document the exact table shape, owner fields,
   local-controller identity, and return behavior. Preserve legacy string
   mappings and fallbacks, including omitted faction, exactly as specified
   by #2515 and its canonical amendments; do not promise a universal
   inverse through the legacy `unit.getFaction` adapter.

   Preserve numeric Z, omitted Z, explicit nil Z, faction-slot precedence,
   and fixed page/binding argument positions. A stale or malformed binding
   remains a refusal before ID allocation or command queueing, returning
   `(nil, "page binding stale")`. Preserve the existing atomic page
   lifecycle admission and ordinary unbound failure convention. A refused
   portal spawn consumes no roster entry or supplies and issues no walk.

2. **Atomic request validation.** Validate profile fields by Lua type and
   validate the entire extra-tag collection before applying any requested
   field. Unknown controllers, malformed tags, wrong-typed owners, and
   malformed profile fields apply no requested controller or extra tags:
   for an otherwise admissible spawn, create the unit with its definition's
   FTS-3 defaults and emit exactly one refusal diagnostic for that request.
   Mixed valid/invalid requests have the same fallback, without partial
   ownership or membership changes and without a script exception. This
   fallback never bypasses a page/binding refusal. Syntactically valid
   minted tags remain accepted under the authoritative tag validator.

3. **Canonical roster membership.** Every locally controlled unit receives
   the same canonical roster team tag, deterministically derived from the
   complete local-controller identity and owned by spawn ingress. This
   covers profile requests, legacy `"player"` calls, portal spawns, and
   explicit `player` location overrides. Ordinary runtime owners cannot
   remove the ingress-owned membership. Overlapping membership under
   another owner retains that owner's provenance and removal semantics.

   During load reconciliation, add any missing canonical ingress-owned
   membership to saved local-controller units. Preserve all existing tags,
   owners, controller, and capabilities, including a same-tag membership
   held by another owner. Backfill is idempotent, logs once per actually
   backfilled unit, emits no backfill warning for an already-correct unit,
   and never fails a load solely because the membership was absent.

4. **Location composition through both paths.** For placed locations,
   update both `spawnUnitContent` and `spawnEncounterUnitContent`. With no
   explicit faction override, use the definition's FTS-3 default profile
   without a controller. With an explicit legacy string, use its complete
   D-26 mapping before adding the occupant group membership:

   - `player` retains local ownership, commandability, and canonical
     roster membership.
   - `debug` retains local commandability and unrestricted-combat
     capabilities without player ownership or roster membership.
   - Other legacy values retain their specified base-profile mapping.

   Add one shared occupant group tag under the location's owner identity
   regardless of the override. Consequently, even a legacy `neutral` or
   `debug` location unit can share group-based alliance; its capabilities
   and ownership remain governed separately. Do not introduce a special
   relation-precedence exception for these overrides.

   Derive both the tag and its owner deterministically and collision-free
   from the full `(WorldPageId, instance_id)` pair. Every occupant of one
   instance shares that group; distinct instances, including equal
   integers on different pages, have distinct tags and owners. Use the
   stored instance identity, not a newly allocated or inferred identity.

   Preserve registered encounter prefixes, exact existing unit IDs and
   homes, missing-slot-only retries, authored `contents` ordering, and
   one-time content/encounter lifecycle behavior. Hand-stamped locations
   without a placed instance retain their existing no-encounter behavior.
   Remove only `faction: hostile` from the shipped `ruin_small` unit entry;
   its nomads then carry authored `nomad` identity plus the occupant tag.

5. **Relations and control remain separate.** With no overriding live
   cause or shared controller/group, shipped nomad occupants are hostile
   to acolytes through the base table and neutral to wildlife. Occupants
   sharing a location group are allied even when their authored
   affiliations differ. Nomads from different locations are also allied
   through `nomad`, while retaining distinct occupant tags for future
   D-37 report scopes. Preserve live-cause precedence and directionality;
   this issue changes no relation consumer or policy.

   The debug overlay continues to pass `"debug"`. Preserve ownership,
   commandability, and discovery behavior under the selected mappings;
   alliance alone grants none of those properties. Demonstrate the same
   definition as an uncontrolled location occupant and a local-roster
   unit: identical authored identity, different controller and group
   memberships, and the corresponding authoritative policy answers.
   In particular, absent a live override, a locally controlled nomad is
   allied to its controller's acolyte roster while an uncontrolled nomad
   with no shared group is hostile to that roster.

6. **Persistence and documentation.** Preserve roster and occupant tag
   identities and every membership owner through the FTS-3 wire. Do not
   change serialized shapes, component versions, or retained codecs.
   Non-wire restore/reconciliation changes are allowed. Do not reseed
   saved authored identity from current definition defaults; roster
   backfill is the bounded reconciliation described above.

   Document the profile request and refusal behavior, location YAML
   `faction` semantics, and deterministic group/owner identities at their
   owning boundaries. Update `scripts/CLAUDE.md` and the applicable
   persistence inventory/contract notes. Required documentation and
   behavioral evidence are completion criteria of this implementation PR
   before final review and merge.
