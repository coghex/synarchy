# Where the headless suite's CI time goes (#2743, CIR-14)

Measured 2026-09-30 against `master@9a274311d` on the CI image
`ghcr.io/coghex/synarchy-ci:ci-f90dae38568ffe9f` (GitHub-hosted
`ubuntu-latest`). This is an investigation report for
[`docs/ci_runtime_reduction_design.md`](ci_runtime_reduction_design.md)
CIR-14: it records measurements and proposes a lane partition for CIR-15.
It changes no workflow, runner script or test.

**Headline.** Nearly every second of the suite is now attributed: over five
ordinary CI runs the examples' own durations account for 99.7 % of Hspec's
`Finished in` (1125 s mean), leaving a 2–3 s residual. The shared-world block
is 480 s (43 %) and generates all nine `sharedWorld` keys; two
`Solidification` groups outside it add another 237 s. **Two lanes** —
`Spec.hs:456`–`598` (the shared-world block and the seven statements before
`PagedMapArtifact`, 586 s) and `Spec.hs:601`–`1318` (578 s including the
post-suite steps) — fit the **853 s per-lane budget** that D-15's twenty-minute
median implies at today's median build, and predict a **933 s median PR run**
against 1507 s today. Running each lane alone on CI covered every example
exactly once and matched the prediction to within runner-speed variance. The
full tier's one example costs 38–59 s but adds about nothing, because it moves
the `(42,128,3)` generation rather than repeating it.

## 1. Method

### What was collected, and how

The CI log names only the twenty slowest items (`--print-slow-items=20`,
from issue #2277), which floors each duration to whole milliseconds and
drops every item that floors to zero. To time every example, the suite
ran on CI from a **temporary collection commit** that `tools/headless_lane_measurement.py
instrument` generates from an unmodified checkout. It changes two files and
nothing else:

- `test-headless/Spec.hs`: every top-level statement of `main`'s do-block is
  wrapped in `describe "@G<line>"`, and every statement of a top-level
  do-block also in `describe "@S<line>"`, where `<line>` is that statement's
  line in the unmodified `Spec.hs`. A `describe` changes an example's path,
  not what it runs or the order it runs in, so each example lands in exactly
  one group — including examples introduced inside imported spec functions
  and groups with no `describe` of their own — without re-deriving any call
  graph. `main` runs the same spec through hspec's own primitives
  (`evalSpec`, `readConfig`, `runSpecForest`, `evaluateResult`) and tees
  every `ItemDone` event to stdout as one `@@HSPEC-ITEM … @@END` line: the
  example's full path, source location and unrounded duration.
- `test-headless/Test/Headless/Harness.hs`: `sharedWorld` prints
  `@@SHARED-WORLD-GEN (seed,size,plates) <s>` when it generates a key and
  `@@SHARED-WORLD-HIT (seed,size,plates)` when it returns an existing one;
  `withHeadlessEngine` / `withHeadlessEngineNoWorld` time their setup and
  teardown (`@@ENGINE …`). Each record is attributed to the example whose
  `ItemDone` follows it.

`.github/workflows/ci.yml` and `tools/ci-local.sh` were not touched: every
measured run used CI's own command,
`cabal test synarchy-test-headless -v0 --test-show-details=direct
--test-options='--print-slow-items=20 --format=failed-examples'`. The final
pull request leaves `ci.yml`, `tools/ci-local.sh` and `test-headless/`
exactly as on master; the collection commits survive only in the pull
request's history.

### How hspec attributes time (hspec-core 2.11.17)

- An example's duration is measured around its whole action, including any
  `before`/`around` hooks.
- `aroundAll` is `beforeAll` (memoised into the first example's `before`)
  plus `afterAll` (appended to the last example as a cleanup). So an
  `aroundAll withHeadlessEngine` **boot is charged to the first example
  under it and its teardown to the last** — not to "no example", as the
  issue's background assumed.
- A `sharedWorld` generation is charged to whichever example first asks for
  that key.
- `Finished in` is wall time around the whole evaluation; the residual
  `Finished in − Σ example durations` is everything no example owns (runner
  scheduling, formatter output, clock granularity). It is reported as an
  unattributed residual, not as hook time.

### Validity checks the aggregation enforces

`aggregate` refuses to tabulate unless, for every measured run: the
`test-and-audits` job's `Headless test suite` step succeeded; the number of item records
equals the Hspec footer's example count and the pending/failure records equal
the footer's; every example sits in a `@G` group that is a statement of
`Spec.hs` at the recorded commit; and all ordinary runs executed the same
examples in the same order.

## 6. The per-lane budget (requirement 7)

D-15's target is a **median successful PR run under 1200 s**. A lane job's
critical path is the time before it starts, its own setup and build, the
`cabal test` wrapper, its Hspec time, any steps after the suite, and the tail
until the last job finishes. Medians over **21 successful first-attempt
`pull_request` runs of the unmodified workflow** (listed in §9; one rerun
attempt in the same window is excluded because a rerun attempt reports its
earlier attempt's untouched jobs with their original timestamps):

| Component | Median s |
|---|---|
| run start → `test-and-audits` start | 45 |
| job start → `Headless test suite` start (container, checkout, plan, both cache restores, library + executable + test-suite build) | 262 |
| step − `Finished in` (cabal wrapper) | 34 |
| `test-and-audits` end → last job end | 6 |
| **fixed cost per lane** | **347** |
| steps after the suite (save-compat, audio boundary, sdist; they stay in one job) | 33 |
| for reference: whole run | 1507 |
| for reference: run start → `behavior-probes` end / `static-audits` end | 615 / 408 |

**Per-lane budget: 1200 − 347 = 853 s** of Hspec time (plus the post-suite
steps, for the lane that carries them) at today's median build. D-14's
per-lane build is inside the 262 s: each lane repeats it from the shared
cache, and in the median run that is an exact-hit build. The design
document's earlier arithmetic assumed a ten-minute build; in this sample the
median is 4.4 minutes.

## 7. Proposed partition (requirement 6)

**Two lanes, each a contiguous range of `Spec.hs` statements:**

| Lane | Statements | Groups | Examples | Predicted Hspec s (mean) | Slowest measured run s | Predicted run s |
|---|---|---|---|---|---|---|
| **1** | `Spec.hs:456`–`598` (everything before `PagedMapArtifact`) | 8, including the whole shared-world block | 758 | **586** (583 + 3 residual) | 606 | **933** |
| 2 | `Spec.hs:601`–`1318` | 414, plus the post-suite steps | 9785 | 578 (542 + 3 residual + 33 audits) | 620 | 925 |

**The longest lane is lane 1 at 586 s** against the **853 s per-lane
budget**, so the partition meets D-15 at today's median build with 267 s to
spare: the predicted median run is **933 s (15.6 minutes)**, against 1507 s
today. At each group's slowest measured time the longer lane is lane 2 at
620 s, still 233 s under budget. The other jobs finish earlier
(`behavior-probes` at 615 s, `static-audits` at 408 s), so the whole
workflow, not just a lane, is predicted under twenty minutes.

Why this shape:

- **The shared-world block stays whole.** It is 480 s against an 853 s
  budget, so D-3's floor is nowhere near binding and no key-affinity split
  (§4) is proposed. Every consumer of every key is in lane 1 by
  construction.
- **Contiguous ranges** are the cheapest selector for CIR-15: one wrapper
  `describe` around `Spec.hs:456`–`598` selects lane 1 and a `--skip` of the
  same name selects lane 2, which is the design's "a new group can only land
  in B" rule, and each lane keeps today's internal order. The split point is
  the exact minimum of the longest lane over all two-way contiguous splits;
  an unconstrained two-way assignment (longest-first bin packing, tried on
  the first run) was only 3 s better, so contiguity costs nothing material.
- **A third lane buys 103 s.** With three or more lanes the shared-world
  block is alone in its lane and sets the floor: 483 s of Hspec, a predicted
  830 s run. That is one more job's build for 1.7 minutes.
- **Headroom against the build.** The partition stays under twenty minutes
  while a lane's setup and build take at most 529 s; 17 of the 21 baseline
  runs were at or under that (p75 316 s → 987 s run; p90 661 s → 1332 s).
  The runs above it are the project-cache fallback builds CIR-17 is
  attributing.

### Validation: each proposed lane run alone on CI

The prediction assumes a group costs the same in a lane as in the whole
suite. To test that directly, each proposed lane ran **alone, in its own
process, on CI** (commits `7dc356fd9` and `2317e1ccc` in §1, which prepend
Hspec `--match` / `--skip` filters for lane 1's eight statements):

| Lane run | Groups | Examples | Predicted s | `Finished in` s | Δ | GitHub step s |
|---|---|---|---|---|---|---|
| lane 1, `36685843626#1` | 8 | 758 | 583.1 | 591.7 | +8.6 s (+1.5 %) | 632 |
| lane 2, `36688271934#1` | 414 | 9785 | 542.4 | 571.0 | +28.6 s (+5.3 %) | 617 |

- **Coverage is exact.** Compared as multisets of example paths, the two
  lane runs together executed all 10,543 examples of the whole suite, none
  missing and none repeated. (Two example paths under `Spec.hs:1163` occur
  twice in the suite itself, which is why the comparison is a multiset.)
- **The excess is runner speed, not a lane cost.** In lane 2 the CPU-bound
  groups ran 5–10 % slower together (`Solidification` 1.059,
  `SolidificationOccupants` 1.064, `FluidWritebackIncarnation` 1.064,
  `Language.Generated` 1.103, the 397 small groups 1.048), while the groups
  that mostly wait on wall-clock timers were unchanged (`World.SubMinuteClock`
  1.000, `ChunkPageBinding` 1.000, `DebugConsoleStop` 1.000). A first-use
  cost moved into a lane would appear instead as a fixed excess on the
  lane's earliest groups; lane 2's first group, `PagedMapArtifact`, ran at
  1.035 like the rest. Lane 1's groups ran at 0.95–1.02.
- **Both lanes fit even as measured on these runners:** 592 s and
  571 + 33 s against the 853 s budget.
- These two runs' own setup and build (701 s and 729 s) and run walls
  (1409 s and 1423 s) do **not** measure a lane job: every collection
  commit edits `Harness.hs`, which recompiles its dependents, and
  pull-request runs never write the project cache, so each paid a large
  test-suite rebuild. They validate the Hspec side only; §6's baseline is
  the build-side evidence.

## 8. Caveats

- **Each lane pays its own residual and wrapper.** Both are counted in full
  per lane above (about 3 s and 34 s). Nothing else in this split is shared
  between lanes today: no `sharedWorld` key crosses the boundary, and engine
  boots take milliseconds.
- **The collection tee is not free, but it is small:** the instrumented
  runs' `Finished in` (1107–1168 s) sits around the baseline median
  (1116 s).
- **Runner-to-runner variance dominates run-to-run variance.** The
  baseline's `Finished in` spans 773–1183 s. The proposal's 267 s of
  headroom is sized against that, and the slowest-run column in §7 already
  includes a runner 4 % slower than the rest.
- **The budget is a median statement.** D-15 targets the median run; the
  cache-fallback builds that push some runs past 30 minutes today would
  still push those runs past twenty. That is CIR-17's territory and out of
  scope here.
- **More concurrent jobs.** Two lanes add one job to every pull-request
